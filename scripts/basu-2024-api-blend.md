[S] And joining us is Hester, who has spent real time inside this corpus.
[G] Happy to be here. The one-line version is that the authors argue the tool-use community went all-in on synthetic data generation and, in doing so, walked straight past a decade of high-quality human-annotated data that was already almost the right shape.
[O] Hester, set the scene. What was the state of tool-use data in early 2024?
[G] Two strategies dominated. The first is synthetic generation. ToolLLM produced multi-step REST API data sourced from GPT-4 over a collection of sixteen thousand RapidAPI endpoints. Gorilla generated single-call API data for deep learning libraries, also from language models. Cheap, scalable, and it grew fast. The second strategy is curating task-adjacent datasets by hand, which is higher quality and much slower.
[S] And the complaint about the synthetic route is what, exactly? Because "synthetic data is bad" is a claim I hear constantly and see evidence for rarely.
[G] The paper's argument is narrower than that, and it cites prior work for each link. Synthetic data inherits the bias of the model that sampled it. Prior work has shown it lacks diversity. And separately, prior work has shown diverse data improves out-of-distribution generalization. So the chain is: less diverse training data, more overfitting to in-distribution APIs, worse generalization to APIs the model never saw.
[O] There's a second gap too, though. Not just diversity, but which sub-skill gets covered at all.
[G] Right, and I think that's the sharper half. The authors decompose tool use into three sub-tasks. API detection, meaning given a query, pick the right API. Slot filling, meaning extract the parameter values from the utterance or ask the user for what's missing. And sequencing, meaning write the ordered list of API calls needed to finish the task. Their claim is that existing corpora covered detection and slot filling reasonably well, and sequencing rarely.
[S] Sequencing being the only one that matters for anything multi-step.
[G] That's their bet. And their observation is that task-oriented dialogue and semantic parsing datasets already encode intent, plus parameters, plus order. The Schema-Guided Dialogue corpus. MultiWOZ. TopV2. ATIS. SNIPS. All human-annotated, all multi-domain, all sitting there unused for this purpose.
[O] So what did they actually build?
[G] Ten datasets, assembled three ways. Six are curated as part of this paper, four are taken off the shelf. Cut it the other direction and five are in-distribution, used for training and in-domain testing, while five are held out purely for out-of-distribution testing and never trained on.
[S] Hold on. Six curated and four off the shelf, but five and five for train and test. Those don't line up.
[G] They don't, and it's the detail people get wrong most often. Five of the six curated datasets form the training corpus. The sixth curated dataset, SeqToolQA, is held out and used only for out-of-distribution testing. So the OOD suite is four off-the-shelf benchmarks plus one the authors built themselves. SeqToolQA is theirs, not borrowed.
[O] Walk us through the three curation approaches.
[G] First, language-model-assisted generation, which produces SeqSGD and SeqMultiWOZ. Take a multi-turn human-to-assistant conversation with annotated API calls. For each API call, prompt FLAN-T5-XXL to write a natural-language request for it. Then concatenate those requests into one summarized utterance covering the whole conversation. The gold label is the original API sequence with its parameters.
[S] Why not summarize the conversation directly? That's the obvious move.
[G] They tried the obvious move and report that it failed. The raw conversation also contains API execution results, and feeding that to a summarizer produced a lot of noisy detail. So they summarize the API list, not the dialogue. Then they post-process, dropping any example where the generated utterance doesn't correctly reflect the ground-truth APIs.
[O] And the second approach?
[G] Grammar-based generation, which is fully deterministic. No generative model in the loop at all. SeqATIS and SeqSNIPS come from MixATIS and MixSNIPS, the multi-intent versions of those classic voice-assistant corpora. The problem is those datasets tag which text spans are which slots, but not which parameter belongs to which API. So the authors split each multi-intent utterance back into its original single-intent pieces, parse the inside-outside-beginning tag notation into parameter name and value pairs, and re-merge everything into an ordered sequence of calls.
[S] That's a rule-based transformation over labels a human already wrote. I like that considerably better than a language model in the loop.
[G] The same pipeline gives them SeqTopV2, from a semantic parsing dataset spanning eight domains: alarm, event, messaging, music, navigation, reminder, timer, and weather. That one is by far the biggest, roughly ninety-four thousand training examples. They drop everything labeled unsupported, plus duplicates and ambiguous intents.
[O] And SeqToolQA, the held-out one the authors built.
[G] ToolQA is a dataset designed specifically so that questions cannot be answered from a model's internal knowledge. You have to query an external database. But ToolQA ships template questions and final answers, not the intermediate tool calls. So the authors took ToolQA's own provided reference implementation, the code for how each template question gets answered, and derived the corresponding API sequence from it. Seventeen APIs across six domains, three hundred and fifty-eight test examples.
[S] I want to be precise there, because I have seen this described as hand-mapping. They did not hand-annotate each question?
[G] No. They worked at the template level, off the provided implementation. That's a meaningful difference in both effort and error profile.
[O] Give us the scale.
[G] The in-distribution corpus is about a hundred and fifty-nine thousand training examples, roughly eighteen thousand development, and eleven thousand six hundred test. The conclusion calls that over a hundred and ninety thousand instances, though the table itself adds to a hundred and eighty-nine thousand and change. The out-of-distribution suite is much smaller: seventeen hundred and thirty-seven test examples in total.
[S] Now, six of the ten datasets are the authors' own transformations, and two of those had a language model in the loop. Did anyone check the labels?
[G] Yes, and this is a section that exists only in the ACL camera-ready, not in the arXiv version. They sampled fifty examples from each of the five in-distribution datasets, at least two annotators per dataset, and scored three things. Are the intents correct. Are they in the right order. Are the slot names and values correct.
[O] And the verdict?
[G] Data quality runs from point eight five to one point zero across all five datasets and all three dimensions. Annotator agreement runs from point nine zero to one point zero. [S] I'll give them full credit for that. Plenty of dataset papers from this era shipped without any of it. And the pattern is informative on its own. Slots are the weakest dimension in every single dataset.
[G] Which foreshadows every result that follows.
[O] How is model output scored?
[G] Three metrics, all F one. API F one is exact-match F one over the set of predicted versus gold API names. Parameter F one is exact match over slot names and values for each matched API. And LCS F one is built from the longest common subsequence between the predicted and gold API sequences. Precision is the subsequence length divided by the number of APIs the model emitted, recall is that same length divided by the number in the gold sequence. That's the one that catches ordering rather than just membership.
[S] Exact match on all three. Remember that. It comes back.

[G] Nine open-source baselines in total, and that nine already includes the two externally trained tool models. Three settings. All the fine-tuning uses quantized low-rank adapters, batch size one with gradient accumulation of eight, learning rate five times ten to the minus five.

[O] Let me make the optimist case. The thesis is that a decade of careful human annotation in adjacent fields is a better foundation for tool use than fresh GPT-4 output. And the OOD table supports it. Models fine-tuned on data derived from ATIS, collected in 1990, and SNIPS and MultiWOZ, generalize better to modern tool benchmarks than checkpoints trained on those benchmarks' own synthetic siblings. [S] My deflationary case has three parts. One: the entire comparison rides on exact match, and the paper's own qualitative section shows exact match is undercounting. Gold Date, open paren, three, nine, twenty twenty-three, against a predicted Date with named year, month, and day arguments. All wrong by the metric. All arguably right.
[O] Those are real, but they'd hurt every model in the table roughly equally.
[S] Would they? That's an assumption, and nobody tested it. There's no normalization pass and no human re-scoring, so we cannot bound how much of the gap between the API-BLEND models and the baselines is measurement noise. Second part. ToolLLaMA-2-7B and Lynx-7B were built for pass rate and win rate, soft LLM-as-judge metrics. Here they're graded on strict exact match. The paper says so itself, plainly. They never re-scored those two under their native metrics on the same items, so "our corpus generalizes better" and "our models were optimized for this scorer" stay tangled together.
[G] I'd score both of those to the skeptic, with one caveat. The paper flagging the metric mismatch in its own text is not nothing. It's the difference between an oversight and an acknowledged limitation. But the experiment that would separate the two effects is missing, and it would not have been expensive to run.
[O] What's the third part?
[S] There is no frontier closed model anywhere in this evaluation. Everything is open-source and at most a hundred and eighty billion parameters, and the largest model isn't even fine-tuned. In 2024, anyone deploying a tool-calling system was comparing against GPT-4 with in-context learning. We have no idea whether this fine-tuning recipe beats that or gets crushed by it.
[G] That one I'd score to the skeptic without a caveat. And I'll add a fourth that neither of you raised. Contamination is never discussed. ATIS is from 1990. SNIPS is 2018. SGD and TopV2 are 2020. The OOD tool benchmarks are 2023. Every one of them was public before LLaMA-2, Falcon, MPT, StarCoder, and FLAN-T5 were pretrained, and nobody checked whether any of it is already sitting in those base models.

[S] That's a fair point and I'll take it. The floor is low enough that memorization isn't an obvious explanation for the ceiling.
[G] I'd score that one to the optimist. The other thing I'd credit the authors for is a limitations section that's unusually concrete. They name three. No environment interaction, so nothing embodied where an API call actually changes the world. English only. And crucially, a real query often has multiple correct API sequences, while this dataset only ever carries one gold answer.
[S] That last one is the deepest problem in the paper, and it's in their own limitations section rather than mine.
[G] It is. And they go further than most: they lay out three concrete fixes. Store all the alternate gold sequences and score against each. Or, if the APIs are actually executable, score the final answer instead. Or fall back to an LLM judge computing a win or pass rate, which is, of course, precisely the metric they criticized the baselines for using.
[O] That's a nice circle.
[S] It's the whole tension of the field in one paragraph. Strict metrics are reproducible and they undercount. Soft metrics capture semantic correctness and can't be trusted across papers.
[O] So what changes if this holds?
[G] Two things concretely. First, dataset recycling becomes a legitimate strategy again. There's a great deal of human-annotated intent-and-slot data in dialogue and semantic parsing that maps onto tool calling through a deterministic transformation, and this paper is an existence proof that the transformation is worth the effort. Second, for evaluation practice, it's a clean demonstration that a benchmark's metric can be the thing that decides its headline result. Change exact match to anything softer and the ranking might move.
[S] The generalizable lesson for anyone building an eval: if your own qualitative section documents systematic false negatives, you owe your reader a bound on their size. That's usually a day of work.

[G] My takeaway from the paper: curating and transforming existing human-annotated datasets from adjacent domains yields training data whose diversity generalizes better to unseen APIs than the synthetic corpora it was compared against, measured by exact match, with all the caveats that metric implies.
