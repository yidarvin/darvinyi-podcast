[O] Okay, so how do they build it? Because "simulate a hospital" is a very large sentence.
[G] The clever move is that they do not simulate anything bespoke. They stand up a FHIR-compliant server. FHIR, spelled F H I R, Fast Healthcare Interoperability Resources, is the interoperability standard that most commercial electronic health record vendors already support. They run the open source HAPI FHIR server in a Docker container on a Google Cloud virtual machine, load real patient data into it, and expose the same REST interface a hospital's own endpoint would.
[S] So the agent is talking to a standards-compliant interface rather than a toy API. That is a legitimately good decision.
[G] It is the best decision in the paper. It means a task written against this environment could in principle migrate to a live system unchanged, which is a claim almost no agent benchmark can make. They are careful to say the container should not be used in production, no security implementation, no enterprise logging. But the API surface is the real one.
[O] And the data inside it? This is where I get nervous, because "realistic patient records" usually means somebody generated them with a language model.

[O] And the agent scaffold?
[G] Deliberately simple, and they say so. It is built on the AgentBench framework and inspired by the Berkeley function calling leaderboard. The agent sees nine FHIR functions. Condition search, lab search, vital search, vital create, medication request search, medication request create, procedure search, procedure create, and patient search. Each round it must emit exactly one of three things. A bare GET request, a bare POST with a JSON payload, or a finish call with the answer. No other text permitted. Maximum eight rounds per task. Temperature zero for everything except the reasoning model.
[S] And the scoring is single attempt.
[G] Pass at one throughout, and they argue for it explicitly rather than defaulting to it.
