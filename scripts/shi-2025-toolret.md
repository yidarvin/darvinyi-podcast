[S] Set up the gap then. What were tool-use benchmarks doing before this?
[G] Pre-annotating. Tool Bench and Tool Ace both hand each task roughly ten relevant tools up front, and the agent is scored on whether it uses them correctly. So the retrieval step — choose ten candidates out of tens of thousands — is assumed away entirely.
[O] Which is a fair simplification if retrieval is easy.
[G] Which is exactly the assumption the authors test first, in a pilot on Tool Bench. They remove the officially annotated toolset and substitute tools actually retrieved by five off-the-shelf retrievers. With the oracle toolset, G P T three point five turbo has a pass rate of sixty-four point two. The best of the five retrievers lands ten point one below that, and ColBERT v two recovers only twenty-seven point three recall at ten.
[S] Five retrievers, one dataset, one agent model. That is a motivating figure, not evidence.
[G] Agreed, and to be fair the paper treats it as motivation. It is Figure one, in the introduction. The evidence is meant to be the benchmark itself.
[O] So describe the benchmark. What did they build?
[G] It is an assembly job more than a collection job, and that is the honest framing. They pull query-tool pairs out of more than thirty existing tool-use datasets — published benchmarks like Tool Bench, Tool Eyes, MetaTool, A P I Bank and Gorilla, conference resource tracks like AppBench and ToolLens, and open community datasets — everything released between August twenty twenty-three and December twenty twenty-four. Then they deduplicate the overlapping toolsets, K-means cluster each source dataset's queries and sample one task per cluster so a large dataset cannot dominate a small one, and reformat all of it into the shape M T E B uses.
[S] Final size?
[G] Seven thousand six hundred and fifteen retrieval tasks over a corpus of forty-three thousand two hundred and fifteen tools. And they split it three ways by the format of the tool documentation rather than by domain. Web A P I is structured Open A P I style JSON — thirty-six thousand nine hundred and seventy-eight tools, four thousand nine hundred and sixteen tasks. Code Function is function signatures, three thousand seven hundred and ninety-four tools and nine hundred and fifty tasks. Customized App is free-form natural language, two thousand four hundred and forty-three tools and one thousand seven hundred and forty-nine tasks.
[O] Why split on format rather than on what the tool actually does?
[G] Their argument is that format is the dimension that genuinely varies once you merge thirty datasets, and that it gives an interpretable read on whether a retriever's weakness is about representation or about domain. They also say in the discussion that they would like to add three more cuts in future work — query length, number of target tools, and lexical overlap — which tells you they know format alone is thin.
[S] There is a second half to the design, the instructions.
[G] Yes, and that half carries most of the paper's findings. Every query is also paired with a generated natural-language instruction describing what sort of tool to look for. Three human experts hand-write one hundred seed instructions, then G P T four o generates one per task by in-context learning, sampling from a pool that grows to include previously generated instructions so the outputs stay diverse.
[O] Did they check the generated instructions?
[G] They did, and it is better than most benchmarks manage. Five reviewers scored them on four criteria. Eighty-nine point two percent correctly and comprehensively describe the target tool's features, only five point nine percent show any hallucination, and inter-annotator agreement is a Cohen's kappa of zero point seven four three. The roughly eleven percent flagged as mismatched were manually revised rather than discarded, which matters — the final instruction set is partly human-repaired, not raw model output.
[S] Metrics.
[G] Four, all at K equals ten. N D C G at ten for ranking quality, recall at ten, precision at ten, and Completeness at ten, which they borrow from COLT. Completeness is the interesting one, because it is binary per task. One if every target tool for that task is in the top ten, zero otherwise.
[O] So that column is an exact-full-match rate, not partial credit.
[G] Exactly that. Which makes it strictly harsher than recall for any query with more than one target, and you can see the gap open up in the tables. Each metric is then reported under two input conditions: query alone, which the paper calls without-instruction, and the query concatenated with the generated instruction. That toggle is the cleanest thing in the experimental design — same models, same corpus, one variable moving.

[G] Let me score that carefully, because you are each partly right. The control is real and it is decisive about magnitude. Most of the difficulty in the headline numbers comes from corpus size and cross-dataset confusability, not from some intrinsic property of tool documentation. The skeptic wins that point outright.
[S] Thank you.
[G] But the optimist wins the framing, and I think by more. A deployed agent does not retrieve from the source dataset that happened to annotate its query. It retrieves from whatever tools that deployment has, which is exactly a large heterogeneous pool full of near-duplicates. The merged corpus is the realistic setting and the control is the diagnostic. What the paper should have done is put them side by side in the main text and say that out loud.
[O] And the one-to-many labelling problem underneath all of this?
[G] That is the piece neither the control nor anything else resolves. Because tasks come from thirty-plus sources, a query's true relevant set may extend well past whatever that one source annotated. The paper is candid about it — it names the problem, gives the Bing Search versus Google Search example, and argues that models ought to have fine-grained discrimination anyway, and that superficially similar tools usually differ in parameters and scope.
[S] Which is an argument, not a measurement.
[G] Correct, and I would say it plainly. No experiment in the paper quantifies how often a functionally correct retrieval gets scored as a miss. The control table narrows the pool, which reduces the opportunity for the problem to fire, but it does not measure the rate. A small human study over a few hundred flagged misses would have settled it cheaply.
[S] The other thing that is not in the paper at all is contamination.
[G] Not a word. And it deserved one. ToolRet's tasks are the public test annotations of twenty twenty-three and twenty twenty-four datasets, and several of the evaluated embedders were trained on large synthetic or web-scraped instruction corpora assembled over the same window. The direction of that bias is to flatter the models, so it does not threaten the conclusion that retrieval is hard — but it absolutely threatens any ranking between models, which is what a leaderboard is for.
[O] I want to hand one point back to the paper that the skeptic keeps skipping past. Precision at ten looks catastrophic across these tables. Single digits, mostly. That is not a model failure.
[G] It is not, and the paper does not caveat it anywhere. [O] So what changes if this holds?
[G] The most transferable point is that oracle-toolset agent evaluations are upper bounds and should be labelled as such. Nearly every tool-use benchmark reports one, and on Tool Bench G one alone the gap this paper measures is eleven point four zero points of pass rate.

Five of six cross-encoders made a strong retriever's list worse, and all three L L M re-rankers made it worse. That is a component people bolt on without ever measuring whether it helps in their domain.
